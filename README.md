\# AI Travel Benchmark



A standardized and provider-independent benchmarking framework for the automated comparative evaluation of AI-generated travel plans.



The platform enables multiple Large Language Models (LLMs) from different AI providers to receive the same travel-planning task, generate structured JSON responses, and be evaluated using predefined field-level comparison and deterministic scoring rules.



The framework was developed as research software accompanying the study:



\*\*A Standardized Benchmarking Framework for the Automated Evaluation of AI-Generated Travel Plans\*\*



> Citation information will be updated after publication of the associated research article.



\---



\## Overview



Generative AI systems are increasingly capable of producing complex travel plans. However, directly comparing outputs generated by different Large Language Models is difficult because the responses may differ in structure, completeness, and the amount of information provided.



AI Travel Benchmark addresses this problem by providing a standardized experimental workflow in which different AI systems receive equivalent input conditions and their responses are transformed into directly comparable structured outputs.



The benchmarking workflow follows the general sequence:



1\. A travel-planning request is provided by the user.

2\. The request is combined with predefined response requirements and a structured JSON output specification.

3\. The same combined instruction is submitted to each configured AI provider.

4\. The returned content is parsed into a structured JSON representation.

5\. Corresponding predefined fields are extracted and compared.

6\. Deterministic evaluation rules and predefined field weights are applied.

7\. Category-level and overall scores are calculated.

8\. The evaluated models are automatically ranked.

9\. Comparative results are presented through the web interface.



The current implementation primarily evaluates \*\*structural completeness and information availability\*\*. A high benchmark score does not necessarily indicate factual accuracy, real-time validity, semantic quality, or practical feasibility of the generated travel plan.

\## Configuration



The application reads provider credentials and model configuration from environment variables.



The following variables are used:



```text

OPENAI\_API\_KEY

OPENAI\_MODEL



GEMINI\_API\_KEY

GEMINI\_MODEL



MICROSOFT\_AI\_API\_KEY

MICROSOFT\_AI\_ENDPOINT

MICROSOFT\_AI\_MODEL

```



An example configuration is provided in:



```text

.env.example

```



Example:



```env

OPENAI\_API\_KEY=

OPENAI\_MODEL=gpt-5.6-luna



GEMINI\_API\_KEY=

GEMINI\_MODEL=gemini-3.5-flash



MICROSOFT\_AI\_API\_KEY=

MICROSOFT\_AI\_ENDPOINT=

MICROSOFT\_AI\_MODEL=phi-4-mini-instruct

```



\*\*Do not commit real API keys or other credentials to the repository.\*\*



The Spring configuration references these environment variables rather than storing credentials directly in the source code.

\## Benchmark Methodology



The framework is designed around the principle that heterogeneous AI systems should be evaluated under equivalent experimental conditions.



All evaluated providers receive the same:



\- travel-planning request;

\- response requirements;

\- structured output specification;

\- benchmark conditions.



No provider-specific modification of the standardized benchmark instruction is required by the evaluation workflow.



The standardized instruction is intended to control the experimental input rather than optimize the performance of any individual model.



\---



\## Response Processing



For each configured provider, the framework:



1\. sends the combined benchmark instruction;

2\. receives the generated response;

3\. attempts to parse the returned content as JSON using Jackson `ObjectMapper`;

4\. retains successfully parsed content as a structured `JsonNode`;

5\. supplies the structured response to the field-level comparison and scoring components.



Responses that cannot be successfully processed are recorded as unsuccessful executions.



The framework does not currently perform independent factual verification of the generated travel information.



\---



\## Evaluation and Scoring



The experimental scoring framework consists of seven evaluation categories:



| Category | Number of Fields | Maximum Score |

|---|---:|---:|

| Trip Summary | 6 | 6 |

| Budget Comparison | 7 | 9 |

| Flight Comparison | 9 | 9 |

| Accommodation Comparison | 8 | 8 |

| Legal and Operational Information | 7 | 7 |

| Services | 3 | 8 |

| Additional Information | 6 | 10 |

| \*\*Total\*\* | \*\*46\*\* | \*\*57\*\* |



The relative field weights used in the published experiment were developed with the participation of academic experts in tourism within the research team.



Fields were assigned predefined weights according to their relative importance to the completeness of a structured travel plan. The weighting scheme was finalized before benchmark execution and was applied identically to all evaluated AI models.



The resulting score should be interpreted as a measure of \*\*structural completeness according to the implemented evaluation rules\*\*, not as an independent measure of factual correctness or overall travel-plan quality.



Detailed scoring information is available in:



```text

benchmark/scoring-scheme.md

```



\---



\## Response-Time Measurement



The configured AI providers are invoked sequentially during benchmark execution.



For each provider, timing starts immediately before the provider-specific generation operation and ends after the returned content has been parsed into a structured JSON representation.



Elapsed time is measured using:



```java

System.nanoTime()

```



and converted to milliseconds.



Consequently, the reported time represents an \*\*end-to-end response processing time\*\*, which includes API communication, network transmission, remote provider-side processing, response transmission, and local JSON parsing.



It should \*\*not\*\* be interpreted as an isolated measurement of LLM inference speed.

\## Experimental Results



The experimental application of the framework produced the following overall structural-completeness scores:



| Model | Score |

|---|---:|

| Google Gemini | 57 / 57 |

| OpenAI ChatGPT | 46 / 57 |

| Microsoft Phi | 37 / 57 |



These results should \*\*not\*\* be interpreted as a general ranking of the three AI systems.



They represent the outputs generated under the specific benchmark scenario, model versions, evaluation criteria, and experimental conditions described in the associated study.



The purpose of the experiment was primarily to demonstrate the ability of the framework to process heterogeneous AI outputs under standardized conditions and identify measurable differences at the level of predefined travel-planning fields.

The framework is designed to support further research and development.



Possible extensions include:



\- integration of additional LLM providers;

\- additional travel-planning scenarios;

\- alternative structured output specifications;

\- alternative scoring schemes;

\- factual verification against authoritative or real-time data sources;

\- constraint-compliance evaluation;

\- semantic and consistency analysis;

\- repeated benchmark execution and statistical analysis;

\- expert-assisted evaluation;

\- adaptation to other structured AI benchmarking domains.



\### Adding a New AI Provider



Provider integrations are based on the common `AiProviderClient` abstraction.



A new provider can therefore be integrated by implementing the required provider interface while preserving the common benchmark execution and evaluation workflow.



This design allows provider-specific API communication to remain separated from the common comparison and scoring logic.
